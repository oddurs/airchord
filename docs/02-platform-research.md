# Platform research

Findings that shaped the server and asset setup. Each one changed a decision, so they're recorded
with the decision attached.

## 1. The camera needs a secure context, and that drives the whole server design

`getUserMedia` is only available in a secure context: HTTPS, `file://`, or `localhost`
([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)). Desktop
development on `localhost` is therefore fine with plain HTTP — but the moment you want to try the
instrument on a phone, you're hitting a LAN IP, `localhost` no longer applies, and you need real TLS.

**iOS is stricter than everything else.** Safari refuses `mediaDevices` over HTTP *and* over HTTPS
with an untrusted certificate — where desktop browsers let you click through an interstitial and
carry on. For iOS the certificate has to be genuinely trusted by the device.

**Decision:** a custom Node HTTPS server rather than `next dev`/`next start`, listening on `0.0.0.0`
so LAN devices can reach it, with certificates covering `localhost`, `127.0.0.1` and every LAN
address of the machine.

**Decision:** prefer [mkcert](https://github.com/FiloSottile/mkcert), fall back to an openssl
self-signed cert. mkcert installs a local CA whose root can be installed on a phone, which is the
only route to camera access on iOS. The fallback still works on desktop; the app says so loudly
rather than failing mysteriously.

Installing the CA on iOS takes three steps and the third is the one everyone misses: transfer
`rootCA.pem` (from `mkcert -CAROOT`) to the device, install it under Settings → Profile Downloaded,
then **enable it in Settings → General → About → Certificate Trust Settings**. A manually installed
certificate is *not* trusted for TLS until that toggle is on
([Apple](https://support.apple.com/en-us/102390)).

## 2. Custom servers cost you things

Next's own guidance is that a custom server disables Automatic Static Optimization and rules out
`output: 'standalone'` ([Next.js docs](https://nextjs.org/docs/pages/building-your-application/configuring/custom-server)).

For this app that price is near zero — it is one static client-rendered page with no server routes,
no ISR, no middleware — so local HTTPS is worth it. If server routes are ever added, revisit.

`next dev --experimental-https` exists and generates certificates via mkcert automatically, but it
targets `localhost` and is awkward to point at a LAN IP, so it isn't a substitute here.

## 3. MediaPipe does *not* need cross-origin isolation

Worth checking before reflexively adding COOP/COEP headers, which is the usual cargo cult around
wasm. `SharedArrayBuffer` requires cross-origin isolation — `Cross-Origin-Opener-Policy: same-origin`
plus `Cross-Origin-Embedder-Policy: require-corp`
([web.dev](https://web.dev/articles/coop-coep)) — but the shipped `tasks-vision` wasm bundles
contain **no `SharedArrayBuffer` references at all** (verified by grepping the three bundles in
`node_modules`).

**Decision: do not set COOP/COEP.** They would buy nothing and `require-corp` actively breaks
loading any cross-origin resource, so it's a pure downside.

One header *is* needed: Next infers `text/plain` for `.wasm`, which fails
`WebAssembly.instantiateStreaming` and pushes MediaPipe onto a slower fallback path. `next.config.ts`
forces `application/wasm`.

## 4. Self-hosting the model

`FilesetResolver` defaults to a jsDelivr CDN for the wasm runtime and Google Cloud Storage for the
7.8 MB `hand_landmarker.task`. MediaPipe requires the wasm files be published **without renaming**,
which rules out putting them through a bundler's hashed-asset pipeline.

**Decision:** `scripts/assets.mjs` copies the wasm directory verbatim out of `node_modules` into
`public/mediapipe/` and downloads the model beside it. Both are gitignored and regenerated by
`npm run assets`, which `dev` and `build` depend on. The instrument then works offline and startup
isn't gated on two third-party round-trips. The model gets a one-year immutable cache header.

## 5. Landmark reference

The model returns 21 landmarks per hand, normalised to 0..1 with the origin at top-left.

```
0  wrist
1-4    thumb   (2 MCP, 3 IP,  4 tip)
5-8    index   (5 MCP, 6 PIP, 8 tip)
9-12   middle  (9 MCP, 10 PIP, 12 tip)
13-16  ring    (13 MCP, 14 PIP, 16 tip)
17-20  pinky   (17 MCP, 18 PIP, 20 tip)
```

**Handedness is reported as if the frame were a mirrored selfie.** A raw `getUserMedia` frame is not
mirrored, so the reported label is the opposite of the user's actual hand. `vision.ts` swaps it,
behind a named constant — if hands ever come out reversed, that constant is the one to flip.

Video frames are processed entirely on-device; nothing is uploaded. Worth stating plainly in the UI,
since pointing a webcam at yourself invites the question.
